# Product Vision

## 문제

할 일 관리 도구는 많지만, 대부분 계정을 만들고 데이터를 남의 서버에 두어야 합니다. 터미널에서 일하는 사람은 브라우저나 별도 앱으로 맥락을 옮기는 비용을 매번 치릅니다. 그리고 도구가 서비스 종료되거나 요금제를 바꾸면 축적한 기록을 잃습니다.

## 대상 사용자

터미널에서 하루의 대부분을 보내며 자기 데이터를 자기 기계에 두고 싶어 하는 개인 사용자입니다. 스크립트로 자기 작업 흐름을 자동화하는 데 익숙합니다.

같은 사용자가 항상 터미널에 있는 것은 아닙니다. 할 일 하나를 빠르게 넣을 때는 명령줄이 빠르지만, 쌓인 목록을 훑고 우선순위를 다시 잡을 때는 화면을 넓게 쓰는 편이 낫습니다. 이 두 상황은 다른 사용자가 아니라 같은 사용자의 다른 순간입니다.

## 가치 제안

- 계정도 네트워크도 없이 즉시 시작합니다. 데이터는 사용자의 로컬 SQLite 파일 하나입니다.
- 같은 규칙을 명령줄, HTTP, 브라우저 세 표면으로 제공합니다. 사람은 CLI나 브라우저를 쓰고 스크립트는 API를 씁니다. 세 표면 모두 같은 로컬 파일을 봅니다.
- 저장 형식이 공개되어 있고 사람이 읽을 수 있습니다. 도구를 떠나도 데이터가 남습니다.

## 성공 기준

- 사용자 결과: 설치 후 첫 할 일을 추가하기까지 한 개의 명령이면 충분합니다.
- 일관성: 모든 표면이 같은 입력에 대해 항상 같은 결과를 보여줍니다.
- 신뢰성: 저장에 성공했다고 알린 할 일은 프로세스가 비정상 종료해도 남아 있습니다.
- 안전성: 사용자가 명시적으로 요청하지 않은 삭제나 상태 변경이 일어나지 않습니다.
- 지속 가능성: 저장 형식이 문서화되어 있고 스키마 변경에 마이그레이션 경로가 있습니다.

## 비목표

현재 제품이 의도적으로 해결하지 않는 문제입니다. 이 항목들을 다루려면 먼저 비목표를 옮기는 결정이 필요합니다.

- 다중 사용자와 협업. 인증, 권한, 공유 개념을 도입하지 않습니다.
- 기기 간 동기화와 서버 호스팅.
- 사용자의 기계 밖에서 접속할 수 있는 인터페이스. 브라우저 표면은 루프백에만 바인딩합니다.
- 반복 일정, 알림, 캘린더 연동.
- 하위 작업, 의존 관계, 프로젝트 계획 기능.

## 표면은 로컬 자동화와 로컬 사용을 위해서만 존재합니다

HTTP API가 존재하는 것은 원격 사용을 위해서가 아니라 로컬 자동화를 위해서입니다. 브라우저 표면이 존재하는 것도 원격 접속을 위해서가 아니라 같은 기계에서 목록을 넓게 보기 위해서입니다. 이 구분이 흐려지면 인증 부재가 위험이 됩니다.

브라우저 표면이 생기면서 이 구분은 문장이 아니라 코드가 지킵니다. 서버는 `127.0.0.1`에만 바인딩하며, 이는 전제가 아니라 강제되는 제약입니다. 화면이 생겼다는 이유로 "잠깐 폰에서도 보자"는 요구가 뒤따르기 쉽고, 그 순간 인증 없는 API가 네트워크에 열립니다.
