# T-0004: 여러 조직 CRUD와 조직별 작업 공간

## 확인과 원칙
현재 OrgState, executeCommand, replay는 단일 조직 엔진이며 Store는 전역 이벤트 목록을 직렬화한다. 삭제는 논리 삭제와 epoch 분리, 데모는 명시적 DemoSeeded 및 기존 51개 이벤트 패턴 호환을 구현했다. 이를 조직별로 재사용하여 레지스트리를 추가한다. 기존 사용자 파일을 마이그레이션 목적으로 재작성·삭제하지 않으며 실제 데이터 CRUD는 수행하지 않는다. 검증은 /tmp 가상 저장소에서 한다. 관련 경로의 하위 AGENTS.md는 없다.

## 최소 변경 설계
- Registry는 OrgId별 OrgState 및 해당 조직 이벤트 스트림을 가진다. 기존 도메인은 한 조직의 이벤트만 받아 동작한다. 조직 내 사람/목표/지표/회고 ID는 다른 조직과 같아도 된다. 조직 ID는 활성 레지스트리 내 유일하며 삭제 후 재생성 시 새 epoch를 시작한다.
- 신규 이벤트는 OrganizationScoped OrgId OrganizationEvent 같은 래퍼를 권장한다. 기존 StoredEvent 생성자와 구형 JSON은 그대로 유지한다. 신규 이벤트만 scope로 감싸 저장하고 외부 요청으로 임의 래퍼를 받지 않는다. 레지스트리가 한 단계 unwrap하여 해당 OrgState에 적용한다. 중첩 scope와 내부 OrganizationCreated/Deleted/Goal 조직 ID 불일치는 거절한다.
- 구형 unscoped 이벤트는 원래 순서대로 가장 최근 unscoped OrganizationCreated의 조직에 귀속시킨다. 구형 Deleted가 epoch를 종료한다. scoped 이벤트는 이 구형 해석 커서를 변경하지 않는다. 신규·구형 혼합 로그를 재시작해도 같은 소속이어야 한다. 변환은 메모리 projection에만 적용하고 원본 이벤트를 재인코딩한 마이그레이션 파일을 만들지 않는다.
- 전역 storedSeq는 모든 조직에 걸쳐 연속 증가한다. 조직 version은 해당 조직에 적용된 마지막 전역 seq로 두어 타 조직 쓰기 때문에 수정·삭제 충돌이 생기지 않게 한다. 같은 조직 ID 재생성에도 마지막 seq가 증가하므로 오래된 확인창은 거절된다.

## 구현 단계
1. 레지스트리 replay/read helper를 추가한다. 활성 조직 목록, 특정 조직 상태, 특정 조직 현재 epoch 이벤트, 저장소 전체 감사 읽기를 분리한다. 원본 감사는 내부 저장용이며 공개 /events는 반드시 해당 조직 현재 epoch만 반환한다.
2. Store에 대상 OrgId를 받는 명령 실행을 추가한다. 같은 MVar 잠금에서 레지스트리를 읽고 해당 조직의 actor/참조/명령을 검증한 뒤 전역 seq를 부여하여 한 번 저장한다. 생성 명령은 ID 중복을 레지스트리에서 검사한다. 삭제는 그 조직만 초기화하며 다른 조직 상태·version·이벤트를 바꾸지 않는다.
3. RenameOrganization 같은 명령과 OrganizationRenamed 이벤트를 추가한다. 이름 1~10000자 검증, expectedVersion 비교, 이름만 변경하고 ID/createdAt/데모 provenance를 유지한다. 버전은 정수 필수이며 잘못된 이름은 400, 없는 조직은 404, 중복 ID·오래된 version은 409이다.
4. 조직 CRUD API를 제공한다: GET/POST /api/organizations, GET/PATCH/DELETE /api/organizations/:oid. 목록 응답은 {organization,version,demo,peopleCount,goalCount}[]이며 상세는 같은 summary 객체를 반환한다. scoped dashboard는 기존 shape(organization/version/demo/people/goals 등)를 유지한다. PATCH는 name+expectedVersion, DELETE는 confirmName+expectedVersion이다. scope가 명시된 /api/organizations/:oid/dashboard, /people, /goals, /compiler, /graph, /events, /reviews 및 기존 하위 쓰기 경로를 제공한다.
5. 기존 /api/dashboard, /people 등 unscoped 경로는 활성 조직이 정확히 하나일 때만 호환한다. 여러 조직이면 409와 명시적 조직 경로 안내를 반환하며 서버 전역 selected 조직을 만들지 않는다. 조직이 0개인 초기 조회는 기존 온보딩 호환을 유지할 수 있지만 참조가 필요한 쓰기는 조직 없음으로 거절한다. POST /api/organizations와 /api/demo는 조직 선택과 무관한 레지스트리 작업이다.
6. 데모는 다른 일반 조직이 존재해도 별도 조직으로 추가할 수 있다. 활성 데모 ID 중복만 409이고 삭제된 데모 ID는 새 epoch로 재생성할 수 있다. 전체 시드는 한 번 저장하고 기존 일반 조직을 건드리지 않는다. 51개 구형 시드와 52개 표식 시드 인식은 해당 조직 스트림을 unwrap한 뒤 유지한다. make demo는 기존 저장소의 여러 조직과 삭제 상태를 보존하고 삭제한 데모를 자동 부활시키지 않는다.
7. UI의 기본 진입은 조직 목록이다. 목록 카드에 이름·구성원/목표 수와 상세 열기, 등록 폼, 데모 추가를 제공한다. 상세에는 이름 수정과 기존 조직 삭제 설정을 제공하며 선택한 조직으로 기존 네 화면을 연다. 항상 조직 목록으로 돌아가는 경로와 현재 조직 표시를 둔다. 삭제 뒤 다른 조직은 목록에 남고 한 조직도 없으면 등록 안내를 보인다.
8. 모든 브라우저 조회는 request token과 시작 시점의 orgId를 고정한다. 조직 A의 늦은 응답이 B 화면을 덮어쓰면 안 된다. 폼 제출은 폼을 연 조직 ID로 URL을 만들며 submit 도중 선택 변경에도 다른 조직으로 전송되지 않아야 한다. 조직 전환·목록 이동 시 삭제/수정 확인 snapshot을 폐기한다. 삭제/수정 snapshot의 이름·ID·version은 확인 시점에 고정하고 409 시 재조회·재확인을 요구한다.
9. README를 다중 조직 사용법, CRUD/조직 scope API, 단일 조직 API 호환 조건, 논리 삭제와 감사 보존, 기존 파일 무마이그레이션 호환에 맞춰 갱신한다. 의존성 추가 없이 기존 Haskell/JS를 사용한다.

## tester / reviewer 수락 기준
- A/B 조직 등록·목록·상세·이름 변경·삭제·같은 ID 재생성 및 restart 복원. 한 조직 삭제 후 다른 조직의 모든 컬렉션과 version이 동일함.
- 두 조직에 같은 person/goal/review ID를 사용해도 결과·권한·회고·graph·compiler·감사 기록이 격리됨. A 전용 사람을 B의 actor, owner, reportsTo, reportedBy, decisionOwner로 참조하거나 A 목표/부모를 B에서 참조하면 거절됨. Goal.organization과 URL 불일치 거절.
- A 수정 중 B 쓰기는 불필요한 version 충돌을 만들지 않음. 같은 조직의 동시 수정/삭제는 한 요청만 성공하며 오래된 snapshot은 409. 실패 저장은 모든 조직의 상태와 파일을 보존함.
- 신규 scoped 스트림, 구형 단일 조직 스트림, 삭제/재생성 구형 스트림, scoped와 구형 혼합 스트림의 replay 동등성. 읽기만으로 기존 파일 바이트가 변하지 않음. 전역 seq 연속 및 조직별 최신 seq 정확성.
- 일반 조직 존재 시 원자적 데모 추가·데모 중복 거절·데모 삭제 후 재시드·다른 조직 보존. 기존 51/52개 데모 인식 및 make demo 재시작 보존.
- API scoped GET/POST/PATCH/DELETE 및 모든 하위 경로. 1개 조직 unscoped 호환과 2개 조직 unscoped 409. 목록에 삭제 조직이 남거나 현재 epoch API에 과거 감사가 노출되지 않음.
- /tmp 서버 브라우저에서 등록 → 목록 → 상세/수정 → 조직 전환 → 기존 네 화면 → 지정 조직 삭제를 실제 체험한다. 느린 A 응답/빠른 B 응답 경쟁, 진행 중 폼 제출 뒤 조직 전환, 삭제창 조직 전환 취소를 검증한다.
- make test 및 build/lint를 완료하고 독립 reviewer가 격리·호환·수명주기·원자성을 승인해야 완료한다. planner는 이 파일만, backend coder는 src/와 서버 연결·README·manifest, frontend coder는 static/만, tester는 test/를 담당한다. 병행 작업의 API 계약은 위 summary/detail/PATCH/scoped dashboard 형식으로 고정한다.
