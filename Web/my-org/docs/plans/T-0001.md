# T-0001: Haskell 조직 운영체계 MVP

## 요청과 확인한 사실
첨부 요청의 중심은 Task 관리가 아니라 Organization → Goal → Ownership → Authority → Result → Evaluation → Learning이다. 단일 최종 책임자, 충분한 권한, KPI가 없으면 활성화할 수 없어야 한다.

저장소에는 Types와 Goal/Event/Evaluation/Review/Graph/Compiler/Analysis 8개 도메인 모듈이 있다. API, 영속 저장소, 웹 화면은 없고 app/Main.hs는 존재하지 않는 Lib를 import한다. test/Spec.hs는 자리 표시자다. package.yaml에 Servant/Warp/PostgreSQL/Hspec/QuickCheck 등 필요한 의존성이 이미 선언돼 있다. 검사한 src/app/test 안에 하위 AGENTS.md는 없다. 셸 명령과 실제 컴파일은 planner 역할에서 실행하지 않았다.

## 구현 범위
기존 도메인을 재사용하여 한 프로세스에서 실행 가능한 로컬 웹 MVP를 완성한다. 기본 저장소는 외부 서비스 없이 실행되는 이벤트 파일이며, 이미 선언된 postgresql-simple을 활용한 PostgreSQL 선택 저장소도 제공하되, 명시적으로 지정된 로컬/테스트 연결만 사용하며 자동 프로덕션 DB 접속은 금지한다. 실사용 외부 ERP/CRM 권한 동기화 및 LLM 호출은 향후 확장으로 명시한다. 단일 조직 로컬 MVP로 범위를 한정한다. 실제 계정 인증은 구현 범위에 포함하지 않으며 감사 actor는 인증된 신원이 아니라 요청에서 지정한 기록 주체임을 명확히 한다. 권한 모델과 접근 제어를 구분하고 서버는 기본 루프백에 바인딩한다.

## 단계
1. 빌드 연결: Lib 또는 적절한 서버 엔트리 모듈을 만들고 app/Main.hs를 연결한다. 기존 manifest를 필요한 수준으로 갱신하고 기존 Stack 명령의 Makefile build/test/run 래퍼를 추가할 수 있다. 의존성을 추가하거나 올리지 않는다.
2. 명령 처리 경계: 조직/사람/목표 생성, 책임자 지정, 권한 부여·회수, 활성화, 결과 보고, 평가, 회고, 전략 변경을 검증 후 StoredEvent로 기록한다. 식별자 중복·미존재·소속 불일치·유효하지 않은 날짜/숫자/텍스트를 거절한다. 존재하지 않는 책임자나 회고 결정 담당자도 거절한다.
3. 불변식 보강: validateDraft에 빈 KPI/설명, 지표 방향과 목표값 모순, 음수 예산, 비유한 숫자 검사 등을 추가한다. 권한 축소/회수 후 관련 활성 목표가 무효 상태로 남지 않도록 재검증하여 비활성화하거나 변경을 거절한다. GoalActivated 이벤트 적용만으로 검증을 우회하지 않도록 외부 쓰기 진입점을 단일화한다.
4. 저장소: 이벤트 순번·시각·행위자를 서버에서 부여한다. 쓰기 실패 시 메모리 상태도 성공한 것처럼 바뀌지 않아야 한다. 동시 쓰기를 직렬화하며 재시작 시 저장 이벤트를 재생한다. 손상 파일은 조용히 비우거나 덮어쓰지 않는다. 샘플 데이터는 빈 저장소에만 명시적으로 초기화한다.
5. HTTP JSON API: POST /organizations, /people, /goals, /goals/:id/owner, /goals/:id/authority, /goals/:id/activate, /goals/:id/results, /evaluations, /reviews와 GET /organization, /people, /goals, /dashboard, /compiler, /graph, /events, /reviews를 제공한다. 기존 타입에 맞춰 /api 접두사를 일관되게 적용할 수 있다. 없는 대상은 404, 잘못된 입력은 400, 상태 충돌은 409로 설명 가능한 오류 JSON을 반환한다.
6. 네 화면: Goal Dashboard에 목표 생성·선택·활성화·결과 입력·평가와 조직/구성원 설정을 연결한다. Responsibility Map은 목표·최종 책임자·KPI·필요/보유 권한·상태를 보여주며 책임자 변경이 가능하다. Authority Map은 구성원별 권한·예산 편집과 집중도/부족 진단을 보여준다. Review/Learning History는 결과·평가·결정·담당자·기한·학습 입력 및 감사 타임라인을 보여준다. 컴파일러 코드와 원인을 화면에서 확인할 수 있게 한다. 안전한 DOM 텍스트 렌더링, 로딩/오류/빈 상태, 좁은 화면을 처리한다.
7. 컴파일러/그래프: 기존 O001/O017/O020/O031/O040 등 진단과 구조 분석을 API·화면에 연결한다. 집중도는 권한 종류와 예산 보유를 세는 규칙 기반 추정치라는 의미를 명확히 한다. 공유 지표 충돌과 목표 의존 관계를 보존한다.
8. 문서: 실행·테스트·저장 위치·샘플 데이터·API와 MVP 제한을 README에 기록한다.

## 분담과 잠금
orchestrator는 배정·취합만 담당한다. coder가 src/, app/, static/ 및 기존 빌드 연결용 manifest/README를 맡고 tester는 실제 프로젝트의 test/를 맡는다. planner는 이 계획 파일만 쓴다. 구현 뒤 tester와 reviewer가 동시에 검증하고 모두 통과해야 완료한다.

## 검증 및 완료 기준
- coder가 기존 컴파일 오류까지 해결하고 실행 파일을 빌드한다. Makefile이 없으므로 make test 부재를 기록한 뒤 stack test 또는 cabal test로 실제 테스트한다.
- tester는 책임자/KPI/권한/예산 부족 활성화 거부, 정상 활성화, 권한 회수 후 불변식, 증가·감소 KPI 평가, 이벤트 재생 동등성, 중복/참조 입력 거부, 컴파일러 진단, 회고 경고를 테스트한다.
- HTTP에서 목표 생성 → 책임자/권한 → 활성화 → 결과 → 평가 → 회고가 연결되는 통합 흐름과 오류 응답을 확인한다. 저장소 재개방 뒤 상태 유지 및 실패 시 상태 불변을 검증한다.
- 브라우저에서 네 화면 전환과 핵심 폼 제출을 실제 확인한다. 화면 문자열이 HTML/스크립트로 실행되지 않아야 한다.
- reviewer가 타입/검증 우회, 상태 변경의 원자성, 저장 오류, 감사 기록 및 입력 참조 무결성을 독립 검토한다.

## 남은 불확실성
PostgreSQL 서버와 Haskell 툴체인 실행 가능 여부는 coder/tester가 확인해야 한다. 요청은 광범위한 제품 구상을 포함하지만 첨부 10절이 초기 MVP를 명시하므로 외부 시스템 연결과 AI 추론은 MVP 완성 조건에 포함하지 않는다고 해석했다.
