# T-0003: 조직 논리 삭제

## 확인과 범위
현재 Store는 전체 감사 이벤트를 보존하며 Command를 MVar 잠금 안에서 검증·저장한다. Server의 dashboard/events는 전체 역사 이벤트를 노출하고 seedDemo는 이벤트 목록이 완전히 비어 있어야만 실행된다. make demo는 현재 조직 ID가 데모 ID가 아니면 재시작을 거절한다. 따라서 삭제 명령 추가와 함께 조회 범위·재시드·시작 동작을 조정해야 한다. 검사한 관련 경로에는 하위 AGENTS.md가 없다.

사용자의 요청은 삭제 기능 구현이다. 현재 사용자 조직을 실제 삭제하지 않으며 검증은 /tmp의 격리된 저장소에서 수행한다. 파일/DB를 물리적으로 비우지 않는 논리 삭제로 구현하고 이를 UI와 README에서 분명히 설명한다. 의존성을 추가하지 않는다.

## 구현
1. OrganizationDeleted OrgId 이벤트와 DeleteOrganization OrgId Text Int 명령을 추가한다. 현재 조직 존재, 대상 ID, confirmName의 정확한 조직명 일치, expectedVersion == stateLastSeq를 검증한다. 같은 이름·ID로 재생성된 조직도 과거 확인창에서 삭제되지 않도록 전역 순번을 비교한다. 검증은 Store 잠금 안에서 실행하고 이벤트 하나를 원자적으로 append한다. 조직 없음/대상 불일치는 404, 이름 불일치는 400, 오래된 버전은 409, 저장 실패는 500으로 반환한다.
2. 삭제 이벤트 재생 시 조직·사람·목표·책임·권한·활성 목록·결과·평가·회고·전략 등 현재 상태를 모두 초기화한다. stateLastSeq는 유지·증가시키며 과거 StoredEvent는 그대로 보존한다. 새 OrganizationCreated부터 새로운 조직 수명주기(epoch)가 시작된다. 최신 생성 이벤트 순번을 수명주기 경계로 사용하여 같은 조직/사람/목표 ID 재사용에도 기록이 섞이지 않게 한다.
3. dashboard에 version을 노출한다. 모든 GET projection은 현재 상태만 사용하고 dashboard.events와 /api/events는 현재 생성 이벤트 이후의 현재 수명주기 기록만 반환한다. 조직이 없으면 현재 이벤트 목록은 빈 배열이다. 삭제 전 조직의 사람 이름·목표·회고·감사 내역이 삭제 직후나 새 조직에서 노출되지 않아야 한다. 저장소의 원본 감사 기록은 내부적으로 유지되며 과거 조직 조회 API는 이번 범위에 포함하지 않는다.
4. DELETE /api/organizations/:id는 application/json 본문의 confirmName과 expectedVersion을 필수로 받는다. 현재 1MB 제한과 JSON-only 쓰기 정책을 재사용하고 method별 경로 처리를 명확히 한다. 성공 응답은 200 JSON 또는 204 중 클라이언트와 일치시킨다.
5. seedDemo는 이벤트 전체가 비었거나 검증된 삭제 완료 상태일 때만 허용하고, 현재 조직이 존재하면 계속 거절한다. 새 데모 이벤트는 기존 전역 순번 뒤로 재번호하여 한 번 persist하고 과거 이력에 append한다. 활성 조직에 데이터 병합은 허용하지 않는다. 일반 새 조직 생성도 삭제 후 정상적으로 이어진다.
6. 수명주기와 데모 provenance를 구분한다. 현재 조직이 데모인지 여부는 현재 epoch의 명시적 데모 표시로 판단하고, 단순 조직 ID 일치로 사용자 생성 조직을 데모로 보지 않는다. 기존 데모 파일은 기존 초기 시드의 구조/기록으로 제한적인 호환 판단을 하되 ID 하나만으로 판단하지 않는다. make demo의 시작 모드는 저장소의 데모 출처와 현재 조직 수명주기를 구분하여 최초 빈 저장소만 자동 초기화한다. 삭제 이력이 있으면 자동 재시드하지 않고 빈 화면을 유지한다. 해당 데모 저장소에서 사용자가 새 일반 조직을 만들었어도 재시작 때 보존·복원하며, 원래부터 unrelated 일반 조직이 들어 있던 저장소를 덮어쓰지 않는다.
7. Dashboard 하단에 명확한 조직 설정/조직 삭제 섹션을 둔다. 삭제 범위(구성원, 목표, 권한, 결과, 평가, 회고, 전략)와 감사 기록이 파일/DB에 남는 논리 삭제라는 점을 설명한다. 열기 → 조직명 입력 → 취소/조직 삭제 버튼을 제공하며 이름이 맞기 전 삭제 버튼을 비활성화한다. 확인창을 연 시점의 ID·이름·version을 고정한다. 충돌이면 새 상태를 조회하고 사용자가 다시 확인하도록 하며 자동 재시도하지 않는다. 취소는 네트워크 쓰기가 없다. 삭제 성공 후 온보딩으로 돌아가 새 조직 또는 데모 생성이 가능해야 한다.
8. README에 위치·조작·논리 삭제 의미·동시 변경 거부·삭제 후 재생성·make demo 재시작 보존을 설명한다. 기존 ‘데이터 삭제 버튼은 없습니다’ 같은 설명을 갱신한다.

## 검증
- Domain: 정상 삭제 후 모든 현재 컬렉션 초기화, 원본 감사 유지, seq 증가, 잘못된 이름/ID/조직 없음/오래된 version 거부. 삭제 후 같은 ID 재생성에도 과거 참조와 감사가 섞이지 않음.
- Store: /tmp에서 삭제 저장·재개방 동등성, 저장 실패 시 상태/파일 불변, 변경 명령과 삭제 경쟁 시 version 검사, 반복 삭제 거부, 삭제 후 재시드/일반 생성과 단조 순번. 기존 조직에 시드 거부 유지.
- API: DELETE 입력·HTTP 상태, 삭제 직후와 재생성 후 모든 GET에서 과거 데이터 미노출, 전체 저장 감사 이력은 유지됨.
- 시작 동작: 최초 make demo 초기화, 삭제 후 재시작에서 부활하지 않음, 삭제 후 일반 조직 생성 뒤 재시작 보존, unrelated 기존 조직 비수정.
- UI: 격리 서버에서 삭제 위치 탐색, 잘못된 이름 비활성, 취소 무변경, 정확한 입력 후 삭제, 온보딩·새 조직·데모 재시작 및 충돌 메시지를 실제 조작한다.
- tester의 make test 및 reviewer 독립 승인을 받는다. coder는 src/static/README 등 구현, tester는 test/, planner는 이 계획만 작성한다.
