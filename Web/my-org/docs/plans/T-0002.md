# T-0002: 원자적 데모 시드와 단계별 체험

## 확인한 현재 상태
- Haskell Application은 모든 변경을 Command로 검증하고 이벤트로 반환한다. Store.runCommand는 MVar 잠금 안에서 검증·파일/DB 저장·메모리 갱신을 처리한다. 현재 명령 하나당 하나의 이벤트가 생성된다.
- Server는 /api/dashboard 등 조회와 개별 POST를 제공한다. 네 화면에서 책임자·권한·결과·평가·회고를 실제 수정할 수 있다.
- static/app.js의 demo()는 조직 1개·사람 3명·목표 3개·결과와 회고를 브라우저 fetch로 차례대로 만든다. 한 요청 실패 뒤에는 부분 데이터가 남고 빈 저장소 조건 때문에 재실행할 수 없다.
- 데모에는 정상 매출 목표, 권한 부족 출시 초안, 미지정 유지율 초안이 있지만 위험/이탈/달성/결과 대기 사례와 상위 목표 연결 및 체험 안내가 부족하다.
- Makefile은 run/build/test 등의 Stack 래퍼만 있다. Lib는 MY_ORG_TEST_DATABASE_URL이 있으면 파일 저장보다 DB를 우선한다. 따라서 make demo는 DB 변수를 명시적으로 제거해야 별도 파일을 보장할 수 있다.
- 검사한 src/, src/MyOrg/, static/, docs/, docs/plans/에 하위 AGENTS.md는 없다. planner는 파일 읽기만 수행했고 컴파일/테스트를 실행하지 않았다.

## 목표와 범위
사용자가 한 번의 명시적 선택으로 실데이터와 분리된 풍부한 데모를 만들고, 무엇을 어디서 바꾸면 어떻게 보이는지 직접 확인하도록 한다. 의존성 추가 없이 기존 Command, Store, API와 네 화면을 재사용한다. 기존 데이터는 삭제·초기화·덮어쓰지 않는다.

## 구현 계획
1. 순수한 데모 정의 모듈을 추가한다. 입력은 기준 시각 UTCTime이며 조직·사람·권한·목표·소유·활성화·결과·평가·회고·전략 Command 목록을 생성한다. 모든 시드 변경은 executeCommand를 순차 적용한 임시 상태로 검증하고 StoredEvent를 누적한다. 검증을 우회하여 OrgState를 직접 합성하지 않는다.
2. 시드 전용 Store 진입점은 기존 runCommand와 동일 MVar 잠금 안에서 events == []를 확인하고 전체 명령을 검증한 뒤 persist를 정확히 한 번 호출한다. 실패 시 이벤트/상태 모두 그대로 유지한다. 임의 배치를 외부 API에 공개할 필요는 없다. 연속 순번과 서버 기준 시각을 사용하며 actor가 지정되는 이벤트는 해당 사람이 이미 생성된 뒤여야 한다.
3. POST /api/demo 같은 명시적 초기화 API를 추가한다. 성공 201, 비어 있지 않음 409, 저장 실패 500을 반환한다. 같은 요청 재전송 또는 동시 클릭은 한 번만 성공한다. 시드 식별자를 기존 데이터에 병합하거나 중복 건을 건너뛰는 방식은 사용하지 않는다. 현재 demo()는 API 한 번 호출로 교체하고 대기 중 버튼을 비활성화한다. 오류 뒤에도 상태를 새로 조회하여 다른 탭의 변경을 반영한다.
4. make demo는 MY_ORG_EVENT_FILE=runs/demo/events.json 및 별도 포트(예: 8081)로 실행한다. MY_ORG_TEST_DATABASE_URL은 이 실행에서 제거하여 실제 선택 DB에 접속하지 않도록 한다. 데모가 이미 있으면 그대로 이어서 실행한다. 별도 파일에서도 사용자가 데모 생성 버튼을 눌러 시작하는 흐름을 기본으로 하며, 자동 시드 옵션을 쓰려면 명시적인 데모 모드에서만 빈 저장소 조건을 지킨다.
5. 화면에 접거나 다시 열 수 있는 체험 안내를 배치한다. 안내는 실제 목표 ID와 사람 ID를 연결하여 해당 화면 및 카드/폼을 찾아갈 수 있어야 한다. 진행 상태를 표시한다면 실제 상태에서 판단하고 클릭만으로 완료 처리하지 않는다. 일반 워크스페이스를 데모라고 오인하지 않도록 식별자/데모 메타데이터를 확인한다.
6. README에 현재 기능 요약, make demo 실행, 시나리오 표, 단계별 조작과 예상 결과, 데이터 유지 및 상대 날짜가 시간이 흐르면 상태에 영향을 주는 점을 설명한다.

## 시드 시나리오 제안
목표 수 7~8개, 한글 가상 조직·사람 약 6명을 사용하되 목적 없는 레코드는 늘리지 않는다. 아래는 구현 가능한 기준안이며 식별자는 안정적인 데모 접두사를 권장한다.

| 사례 | KPI 예시 | 초기 상태 | 체험 목적 |
| --- | --- | --- | --- |
| 전사 성장 | 0 → 100점, 결과 없음 | 활성·결과 대기 | 상위 목표와 자식 목표 그래프, 첫 결과 보고 |
| 엔터프라이즈 매출 | 30 → 50억원, 결과 42 | 활성·정상 | 매출 결과를 50으로 보고해 달성 확인 |
| 고객 확보 | 1000 → 5000명, 결과 2200 | 활성·위험 | 목표 진행률과 시간 기대 진척률 비교 |
| 서비스 안정성 | 10 → 0건 장애, 결과 9 | 활성·이탈 | 감소 KPI의 올바른 진행 방향 |
| 고객 유지 | 이탈률 8 → 3%, 결과 3 | 활성·달성 | 감소 KPI 달성과 회고 학습 |
| 신제품 출시 | 0 → 100%, 권한 일부·예산 부족 | 초안·권한 부족 | 권한 보완 전 활성화 거부 및 이후 성공 |
| 신규 파트너십 | 0 → 10건, 책임자 없음 | 초안·미지정 | 책임자 지정과 활성화 |

기준 시각에서 시작 -50일, 마감 +50일로 두면 기대 진척률은 50%이고 위 정상 60%, 위험 30%, 이탈 10%, 달성 100%는 경계값에 붙지 않는다. 시작·마감·결정 기한(+14일 등)은 실행 시점에 상대적이어야 한다. 이벤트 시각은 생성 사실을 보존하고 가짜 과거 감사 기록을 만들지 않는다. 같은 기준 시각을 순수 시드 함수에 전달하면 결정적인 테스트가 가능하다.

구성원은 한글 가상의 CEO, 영업, 제품, 인프라, 고객 성공, 파트너십 책임자 약 6명을 두고 reportsTo를 연결한다. CEO에 권한을 모아 O031 집중도 사례를 만들되 실제 점수 계산상 50%를 초과하는지 테스트한다. 제품 책임자는 ProductLaunch를 보유하지만 Hiring과 필요한 예산이 부족하도록 두어 O017을 만든다. 미지정 목표는 충분한 권한을 가진 사람이 배정받으면 바로 활성화할 수 있게 설계한다. 목표들은 전사 목표를 부모로 연결하여 DependsOn, Owns, Measures, Controls를 모두 볼 수 있게 한다.

회고는 결과·평가·학습·결정·담당자·미래 기한이 있는 좋은 사례 1개 이상과 결정/학습이 없는 사례 1개를 포함하여 O040 경고를 의도적으로 보여준다. 전략 변경 이벤트도 1개 포함한다. 초기 컴파일러 오류·경고는 체험용 사례이며 생성 실패가 아니라는 안내를 넣는다.

## 화면에서 따라 할 체험
1. Dashboard에서 일곱 목표의 다섯 성과 상태와 두 초안을 비교한다. Responsibility Map에서 미지정 목표를 찾고 안내에 지정된 구성원을 책임자로 지정한다. Dashboard의 해당 목표에서 활성화하여 초안이 결과 대기로 바뀌는 것을 확인한다.
2. 권한 부족 출시 목표를 활성화하면 설명 가능한 오류가 표시된다. Authority Map에서 제품 책임자의 Hiring과 필요한 예산을 보완한다. Responsibility Map의 통제율이 100%가 되고 Dashboard에서 활성화가 성공함을 확인한다.
3. 정상 매출 목표의 결과를 50으로 보고하고 평가 기록을 남긴다. 상태가 달성으로 바뀌고 감사 타임라인에 결과·평가 이벤트가 생긴다.
4. Review & Learning에서 같은 목표를 선택해 학습, 다음 결정, 담당자, 기한을 입력한다. 저장된 최신 결과·평가와 새 회고가 나타나는 것을 확인한다.
5. Responsibility Graph에서 전사 목표에 연결된 하위 목표, 사람, 지표, 자원을 살펴본다. 옵션 체험으로 활성 목표의 필수 권한을 회수해 초안 복귀를 확인한다.

## 검증
- 순수 시드: 전체 Command가 정상 검증되고 모든 활성 목표가 validateActive를 통과한다. 조직/사람/목표 수, 5가지 성과 상태, 미지정·권한 부족, 감소 KPI, 회고와 전략, 부모 참조 및 그래프 EdgeKind가 존재한다.
- 시간: 고정 now의 기대 상태를 검사하며 모든 마감과 결정 기한이 now 이후다. 연도가 다른 now로 생성해도 동일 상태 분포가 나온다.
- Store: 빈 파일에서 전체 생성, 연속 순번, 재개방 상태 동등성, 기존 저장소 거부와 바이트/이벤트 불변, 동시 요청 중 한 번만 성공, 저장 실패 뒤 빈 메모리·파일 유지와 재시도 가능을 검사한다. 기존 저장 실패 테스트 기법을 재사용한다.
- API: 단일 초기화 호출 201, 반복 409, 오류 JSON, 생성 뒤 dashboard/graph/reviews/events 연결을 확인한다.
- 브라우저: 데모 생성 후 네 화면, 안내 링크, 책임자 지정 → 활성화, 부족 권한 수정 → 활성화, 결과 보고 → 달성, 회고 저장을 실제 조작한다. 저장 중 버튼과 실패 메시지, 새로고침 후 데이터·안내 상태도 확인한다.
- make test와 make lint/build를 실행하고 reviewer가 원자성·기존 데이터 보존·DB 분리·체험 안내의 사실성을 독립 검토한다.
