# Product

## 목적

GeneralService는 관리자가 업무(Task)를 등록하고, 결과물을 제출·검토·승인한 뒤 여러 승인 업무를 하나의 Outcome으로 조립하는 내부 업무 관리 웹 서비스다.

## 사용자와 역할

| 역할 | 책임 |
| --- | --- |
| 관리자 | Task를 생성·수정·삭제하고 칸반 보드에서 상태를 관리한다. |
| Task Owner | 자신이 맡은 Task의 결과물을 제출한다. |
| Outcome Owner | 제출된 결과물을 승인하거나 수정 요청하고, 승인된 Task로 Outcome을 생성한다. |
| 사용자 | 이메일과 비밀번호로 가입·로그인하고 자신의 표시 이름을 관리한다. |

## 핵심 사용자 흐름

1. 사용자가 이메일, 비밀번호, 표시 이름으로 가입하거나 로그인한다.
2. 로그인한 사용자는 내 프로필에서 표시 이름을 변경하거나 로그아웃한다.
3. 관리자가 제목, 기대 결과물, 담당자와 우선순위를 입력해 Task를 만든다. 새 Task는 항상 `Draft`로 시작한다.
4. Task Owner가 결과물을 제출하면 상태가 `Submitted`가 된다.
5. Outcome Owner가 결과물을 승인하면 `Approved`, 수정 요청하면 `Reviewed`가 된다.
6. 같은 Outcome Owner가 소유한 승인 Task들을 선택해 `Effective` 상태의 Outcome을 만든다.
7. 관리자는 실행 분류(즉시 실행, 계획 수립, 위임, 제거)에서 해당 Task를 확인하고, 별도의 상태 스윔레인(초안, 검토 완료, 제출됨, 승인됨, 효력 발생)에서 도메인 진행 상태를 관리한다.

## 범위와 가정

- 우선순위는 긴급도와 중요도를 조합한 아이젠하워 매트릭스로 계산한다.
- 아이젠하워 매트릭스의 실행 분류와 `Draft`부터 `Effective`까지의 도메인 상태는 독립된 두 축이다. 실행 분류 카드는 Task를 빠르게 찾고 상세 패널을 열기 위한 참조이며, 상태 변경은 상태 스윔레인 드래그 또는 명시적인 업무 처리로만 일어난다.
- 현 버전은 개발용 이메일·비밀번호 인증과 Bearer 세션을 제공한다. Task·Outcome API의 서버 측 역할·소유자 인가는 후속 작업으로 남아 있다.
- 사용자, 세션, Task와 Outcome은 SQLite에 저장되어 정상적인 서버 재시작 뒤에도 유지된다. 세션은 생성 후 24시간 동안 유효하다.
- 개발 환경에서는 활성화된 `SEED_EXAMPLE_DATA`가 빈 DB에 예시 Task를 최초 한 번만 추가한다. 운영 환경은 `SEED_EXAMPLE_DATA=false`로 비활성화한다. 기존 데이터가 있으면 시드를 건너뛰며, 과거 메모리 저장소 데이터는 자동 이관하지 않는다.
- 현재 SQLite 구성은 단일 서버 인스턴스와 로컬 파일시스템을 전제로 한다. 다중 인스턴스·공유 파일시스템 운영은 지원하지 않는다.
- 기존 운영 DB에 마이그레이션이나 복원을 적용하기 전에는 백업·복원 리허설과 별도 사람 승인이 필요하다.
