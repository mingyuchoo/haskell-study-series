# Security

## 현재 보안 상태

이 서비스는 개발·단일 인스턴스 환경을 전제로 한다. 이메일·비밀번호 회원가입, 로그인과 Bearer 세션은 구현되어 있지만 Task·Outcome API는 인증을 요구하지 않는다. `taskOwner`와 `outcomeOwner`도 요청 본문 값으로 전달되므로 현재 소유자 검사는 신원 검증이 아니라 도메인 규칙 검증이다.

## 현재 적용된 통제

- 서버는 JSON 요청을 파싱하고, 제목·기대 결과물·제출 결과물·Outcome 설명의 필수값을 검증한다.
- 제출, 승인, 수정 요청, Outcome 생성 시 도메인 규칙으로 소유자와 상태를 검증한다.
- 잘못된 식별자와 잘못된 입력은 `400`, 존재하지 않는 Task는 `404`로 처리한다.
- 비밀번호는 bcrypt 해시로 저장하며 API 응답에 포함하지 않는다.
- 인증 세션은 생성 후 24시간에 만료되고, 만료된 토큰은 조회 시 삭제한다.
- SQLite 외래 키를 활성화하고 스키마 마이그레이션을 트랜잭션으로 수행한다. 서버보다 새로운 스키마 버전의 DB는 열지 않는다.

## 주요 위험과 권고

| 위험 | 영향 | 권고 |
| --- | --- | --- |
| Task API 인증·인가 부재 | 누구나 Task를 변경하거나 다른 담당자로 가장 가능 | 모든 변경 API에 인증을 적용하고 조직 SSO 또는 인증 미들웨어를 연동한다. |
| 요청 본문 기반 소유자 | 권한 검증 우회 가능 | 인증된 주체에서 소유자 ID를 파생하고 본문 값은 신뢰하지 않는다. |
| SQLite 파일 유출 | 이메일, 비밀번호 해시, 업무 데이터와 유효한 세션 토큰 노출 | DB와 백업 파일의 소유권·권한을 제한하고 저장 매체 암호화와 비밀정보 대응 절차를 적용한다. |
| 세션 토큰 평문 저장 | DB 읽기 권한 탈취 시 세션 재사용 가능 | 세션 토큰 해시 저장, 회전·폐기 정책과 보안 쿠키 기반 전달을 검토한다. |
| 백업 부재 또는 미검증 복원 | 장애 시 영구 데이터 손실 또는 손상 DB 복구 실패 | 자동 백업, 보존 기간, 무결성 검사와 정기 복원 훈련을 운영 정책으로 정한다. |
| SQLite 다중 인스턴스 제약 | 공유 파일 잠금, 쓰기 경합과 애플리케이션 연산 경쟁 | 단일 인스턴스로 운영하고 확장 전 서버형 DB와 명시적 동시성 계약으로 전환한다. |
| 감사 로그 부재 | 변경 추적과 사고 조사가 어려움 | 행위자, 시각, 변경 전후 값을 기록한다. |
| 전송 보안 미명시 | 외부 노출 시 통신 도청 위험 | 운영 환경에서 HTTPS와 보안 헤더를 적용한다. |

## 보안 요구사항(도입 전)

- 모든 변경 API는 인증된 사용자만 호출할 수 있어야 한다.
- 역할과 소유자 기반의 서버 측 인가가 필요하다.
- 입력 길이 제한, 요청 크기 제한, 속도 제한과 구조화 로그를 추가한다.
- 비밀정보는 소스 코드와 로그에 저장하지 않는다.
- `general-service.sqlite3`, WAL·SHM 파일과 백업은 Git에 커밋하지 않고 최소 권한으로 보호한다.
- 기존 운영 DB에 스키마 변경이나 복원을 적용하기 전 일관된 백업과 복원 리허설을 준비하고 별도 사람 승인을 받는다.
- 실행 중인 SQLite DB를 파일 단위로 임의 복사하지 않고 SQLite 온라인 백업 API 또는 정상 종료 후 검증된 절차를 사용한다.
