# AGENTS.md

## 목적

이 저장소에는 Haskell로 작성한 작은 TodoList HTTP API가 포함되어 있다. AI 코딩 에이전트는 `docs/` 아래의 문서를 제품 및 엔지니어링의 단일 진실 원천으로 취급해야 한다.

구현과 문서가 일치하지 않으면, 관찰 가능한 동작을 변경하기 전에 그 불일치를 보고한다.

## 필수 읽기 자료

코드를 변경하기 전에 다음을 읽는다.

1. `docs/PRODUCT.md`
2. `docs/ARCHITECTURE.md`
3. `docs/DATA_MODEL.md`
4. `docs/API.md`
5. `docs/SECURITY.md`
6. `docs/ACCEPTANCE_TESTS.md`
7. `tasks/` 아래에서 할당된 파일

## 작업 흐름

코드를 수정하기 전에 다음을 수행한다.

1. 관련 구현을 검토한다.
2. 짧은 구현 계획을 작성한다.
3. 변경할 파일과 테스트를 식별한다.
4. 마이그레이션, API 변경 및 위험 요소를 식별한다.
5. 승인된 작업만 구현한다.

## 범위 규칙

- 관련 없는 기능을 추가하지 않는다.
- 관련 없는 리팩터링을 수행하지 않는다.
- 명시적 승인 없이 아키텍처나 공개 API 계약을 변경하지 않는다.
- 배포 후에는 기존 마이그레이션을 수정하지 않는다.
- 잘못된 구현이 준수하는 것처럼 보이게 하려고 명세를 다시 작성하지 않는다.

## 아키텍처 규칙

의존성 방향은 다음과 같다.

    인터페이스 -> 애플리케이션 -> 도메인

인프라스트럭처는 애플리케이션이 바라보는 리포지터리 포트를 구현한다.

도메인 코드는 Servant, Aeson, PostgreSQL, HTTP 또는 환경 설정에 의존해서는 안 된다.

## Haskell 규칙

- 최상위 타입 시그니처를 사용한다.
- `-Wall` 빌드에서 경고가 없도록 유지한다.
- ADT, `newtype`, 전함수, 명시적 오류 및 순수 도메인 로직을 우선한다.
- 애플리케이션 데이터에는 `String`보다 `Text`를 우선한다.
- 프로덕션 코드에서 `undefined`를 절대 사용하지 않는다.
- 프로덕션 코드에서 `head`, `tail`, `fromJust`와 같은 부분 함수를 피한다.

## 오류 처리

예상되는 비즈니스 실패에는 명시적 오류 타입을 사용한다. 인프라스트럭처 예외가 HTTP 응답을 통해 직접 노출되어서는 안 된다.

## 데이터베이스 규칙

- 스키마 변경에는 새 마이그레이션이 필요하다.
- SQL은 반드시 매개변수화한다.
- 데이터베이스 전용 행 표현은 영속성 계층 내부에 유지한다.

## 테스트 규칙

테스트 없이는 기능이 완료된 것이 아니다. 모든 버그 수정에는 회귀 테스트가 필요하다.

완료를 선언하기 전에 다음을 실행한다.

    stack build --test --no-run-tests
    stack test

선택 사항인 PostgreSQL 통합 테스트 스위트는 `TEST_DATABASE_URL`을 사용한다. 이 값이 없으면 DB 의존 검사는 pending으로 표시된다.
